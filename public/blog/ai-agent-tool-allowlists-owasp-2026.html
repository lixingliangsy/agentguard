AI agent tool allowlists: why deny-by-default wins

A tool allowlist is an explicit list of the functions an agent may call; everything not on the list is denied by default. It is the cheapest control that meaningfully limits blast radius, because it removes whole classes of failure instead of filtering each one.

Key takeaways

  • Deny-by-default beats blocklisting: you stop failing to enumerate the bad cases.
  • OWASP's Top 10 for LLM Applications includes excessive agency — an agent granted more functionality or permission than its task requires.
  • Allowlists work best paired with input and output filters; neither replaces the other.

Why allowlists rather than blocklists

A blocklist has to anticipate every dangerous call. An allowlist only has to enumerate the calls the agent legitimately needs — a much smaller, reviewable list. When the agent is prompted into something outside it, the call is refused simply because it was never granted.

Building one

  1. List the tasks the agent actually performs, not the tasks it might someday.
  2. For each task, write the minimum tool and the narrowest parameters that satisfy it.
  3. Deny everything else at the tool registry, not in the prompt — prompt-level restrictions can be argued away.
  4. Classify each allowed tool by what it can destroy: read, write, or irreversible external effect.
  5. Require approval for anything in the third class, and log every invocation.
  6. Re-review the list whenever a tool is added or its parameters widen.

Frequently asked questions

Is a prompt instruction enough to restrict tools?

No. Prompt-level restrictions can be talked around. Enforce the allowlist at the tool registry or the execution layer.

What counts as an irreversible external effect?

Sending email or messages, moving money, deleting records, publishing content — anything you cannot take back.

How many tools is too many?

There is no number. The test is whether you can explain, for each tool on the list, which task requires it and what it can destroy.

Do filters replace an allowlist?

No. Filters catch bad content; allowlists remove unnecessary capability. Use both.

Does this cover indirect prompt injection?

It limits the damage one can do. Detecting and blocking the injection itself is a separate input-side control.

Is the review a security audit?

No. It is decision-support that rates calls and suggests filters. A full assessment of the deployment still needs a security review.
